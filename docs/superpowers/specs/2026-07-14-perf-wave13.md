# Wave 13: Performance for Large Meetings (PR-43a)

## Background

Meetily is a long-meeting recorder. Hour-plus recordings produce thousands
of transcript segments (each ~2-3 s of audio). The current data path:

```
[ASR -> segments[]] -> POST /save-transcript (all-in-one) -> SQLite
```

Pain points at scale (>= 1 hour, ~1500+ segments):

| Layer | Symptom | Root cause |
|---|---|---|
| Network | Slow POST > 30 s | one big JSON body (~5 MB) |
| Backend | high peak memory | request body + per-segment insert loop in single async function |
| Frontend | React render hitch | large state update on response |
| SQLite | single transaction | per-segment insert with implicit transaction |

Goal of PR-43a: enable chunked save without breaking the existing
single-shot UX. Backward-compatible.

## Goals

- New `/save-transcript-batch` endpoint: pure append, requires meeting_id,
  rejects batches > `MEETILY_MAX_BATCH_SEGMENTS` (default 500).
- Modify `/save-transcript`: accept optional `meeting_id`. If absent,
  generate new (legacy behavior). If present, append to existing meeting.
- Frontend helper `saveTranscriptInBatches()`: split a large segment
  array into N batches and POST sequentially. Detects >= threshold and
  warns the user.
- 4 locale i18n: chunked-save notice + error strings.

## Non-Goals

- Streaming SSE (deferred to PR-43b)
- ASR engine memory tuning (Tauri/whisper side, deferred)
- DB migration (current schema already stores segments)

## Risks

| Risk | Mitigation |
|---|---|
| Order mismatch between batches | Each segment carries audio_start_time; reorder on read |
| Half-written meeting on network drop | Client retries from last successful batch index |
| Memory still grows on long sessions | Streaming (PR-43b) + chunked UI (PR-43c) |
